# PPT 插入规格

> 标定日期：2026-08-04
> 标定样本：`1806.成长和价值，为何总是跷跷板-横版.mp4` / `-竖版.mp4`
> 4:36 / 30fps / 横版 1920×1080 @3.49Mbps / 竖版 1080×1920 @2.96Mbps

---

## 一、PPT 是全屏替换，不是画中画

到了标红区间，**整个画面换成 PPT**，说话头完全消失；区间结束再切回说话头。没有转场、没有画中画、没有缩放动画，就是硬切。

本样本的段落结构（横版，逐 0.5 秒扫描平均亮度 + 帧间差得到）：

| 区间 | 内容 | 时长 |
|---|---|---|
| 0.00 – 0.50 | 封面 | 0.5s |
| 0.50 – 129.50 | **PPT 第 2 页** | 129s |
| 129.50 – 154.50 | 说话头 | 25s |
| 154.50 – 263.00 | **PPT 第 3 页** | 108s |
| 263.00 – 276.20 | 说话头 | 13s |

**一页 PPT 停留时间很长**（129s / 108s），不是跟着句子频繁翻页。全片只有 2 页幻灯片、4 次硬切。

## 二、字幕行为不变

PPT 区间里字幕照常压在画面上，**位置、字号、样式与说话头段落完全一致**：

| | 本样本 | 460 期（纯说话头） |
|---|---|---|
| 横版字幕描边外框 | y=863..1004 | y=863..1004 ✅ 一致 |
| 竖版字幕描边外框 | y=1272..1350，h=79 | y=1319..1397，h=79 |

竖版位置不同是因为视频带高度不同（见下），但**「字幕紧贴视频带下沿 +9~10px」这条规则两者都成立**。

## 三、竖版：视频带固定 16:9（2026-08-04 定稿）

**已确定：竖版中间画面一律 1080×608（16:9），不再区分是否含 PPT。**

| | 含 PPT（本样本） | 纯说话头（460 期） |
|---|---|---|
| 视频带 | **1080×608**（16:9） | 1080×700（1.54:1） |
| 视频带位置 | y=656 | y=610 |
| 字幕外框 | y=1272..1350 | y=1319..1397 |

**原因**：PPT 是 16:9 的，必须完整显示不能裁。所以整条视频的画面带都做成 16:9，说话头段落也用同一个带（人物因此比纯说话头版本小一些，实测人脸占带高 0.439，纯说话头版是 0.454，接近）。

> **好处**：竖版和横版共用同一个裁剪框（16:9 → 16:9 只是缩放系数不同），PPT 也不用为竖版单独处理。
> 详见 [视觉规格标定-竖版.md](视觉规格标定-竖版.md) 第一节。

## 四、竖版视频内标题

带子变矮 → 上方留白变多 → 标题做得更大：

| | 含 PPT（本样本） | 纯说话头（460 期） |
|---|---|---|
| em | **165px** | 133.5px |
| 行 ink 高 | 145~146 | 118 |
| 行距（ink 顶到顶） | 206px = **1.25 em** | 166px = **1.243 em** |
| 末行 ink 底 | 643（带顶 656，差 13） | 600（带顶 610，差 10） |

**行距倍数 1.25em 是稳定的；字号是按剩余空间目测定的，没有严格规则。**

建议的自动定字号（待确认）：取满足下面两条的最大 em——
1. 标题块 ink 高 ≤ 0.85 × 视频带顶部 y
2. 最长一行宽 ≤ 0.78 × 画布宽

本样本代入得 em=165，与实测完全一致；460 期代入得 153，实测 133.5（偏大 15%）。

## 五、导出参数：**没有**按流程文档改 2K

流程文档写「带 PPT 的视频分辨率改为 2K」，但这条成片实际是 **1920×1080**，码率反而更低（3.49 Mbps，说话头那条是 10 Mbps）——因为大段静态画面压缩率高，剪映「推荐码率」自动降了。

**结论**：按 1080P 出即可。PPT 是矢量感很强的图表，1080P 下文字清晰；若某期 PPT 字特别小再单独提码率。

## 六、PPT 区间在脚本表里怎么标（关键）

**红色 `#f54a45` 的文字区间 = 该区间播 PPT。**

脚本单元格的富文本里，标红的 run 就是 PPT 区间；黑色的是说话头。样本第 1796 行是「黑 / 红 / 黑 / 红」四段，与视频「头 / PPT / 头 / PPT」的四段结构对应。

全表实测：`（插入PPT）` 这个尾注出现 **87 处**，说明这是常规操作，不是个例。尾注有两种写法：
- `（插入PPT）` —— 提示本条需要配 PPT
- `（标红部分插入PPT）` —— 明确说明按标红区间插

### ⚠️ 陷阱：整格样式统一时飞书不返回 `rich_text`

第 1782 行整格都是红色，API 就**只返回 `cell_styles`、不返回 `rich_text`**。原来的 `load_rich()` 直接读 `rich_text`，遇到这种格子会崩——**整格标红或整格删除线的脚本会被整条漏掉**。

已修复：`rich_text` 缺失时回退到 `cell_styles` 并按整格统一处理。回归验证：
- 1782（整格红）→ 900 字，标红 900 字 ✅
- 1796（黑红交替）→ 1276 字，标红 452 字（35%），2 个区间 ✅

另外 `load_rich()` 只读 `cells[0][0]`，**必须传单个单元格的 range**（如 `B1796`），传 `A1796:B1796` 会读到标题列。

### 区间 → 页码映射：已能全自动 ✅（2026-08-04）

**方法：用「手机版录屏」自动识别翻页时间。**

每期除了原始视频（纯摄像机画面），还有一版类似直播的录屏（文件名带「手机」），画面是 **PPT 全屏 + 左下角人像小窗**。这一版忠实记录了每一页的显示时间，扫一遍就能得到完整的翻页时间轴。

**三步：**

1. **对齐时间轴** —— 录屏和原片时长不同（465 期：5375.84 vs 5398.08），必须先用音频包络互相关求偏移。465 期实测在 600 / 1800 / 3000 / 4800 四个点上偏移**恒为 −14.2 秒**（录屏 = 原片 − 14.2），无漂移。
2. **逐点匹配幻灯片** —— `slidematch` 工具把每个采样帧降采样成 64×36 灰度、**屏蔽左下角人像小窗**（左 20% × 下 20%），与 19 张幻灯片做归一化互相关。命中页得分 0.79~0.81，次优 0.39~0.45，**区分度极高**，阈值取 0.55 即可；低于阈值就是「人像全屏」段。
3. **细化边界** —— 先 5 秒粗扫全片定位切换点，再在每个切换点 ±8 秒内以 0.5 秒细扫，精度 ±0.25 秒。

**465 期结果**（存于 `02-过程/465期-红利指数/PPT时间轴.json`）：

| | |
|---|---|
| 0 – 80.45s | 人像全屏（开场） |
| 80.45 – 1751.95s | **第 1 页 → 第 19 页，严格顺序播放，不跳页不回看** |
| 1751.95s – 结束 | 人像全屏（后半段互动问答） |

**交叉验证**：人工做的 1806 切片用了第 2、3 页，其内容在原片约 217s 处；按本时间轴 217s 正落在第 2 页区间（86.45–236.95），且第 2→3 页切换在 236.95s，与该切片里两段 PPT 之间的说话头间隙对得上。✅

**命令**：

```bash
# 1) 求偏移（多点验证是否恒定）
rms <原片> 1800 1860 100 > tpl.txt
rms <录屏> 1740 1920 100 > hay.txt   # 再做互相关

# 2) 粗扫 + 细扫
slidematch <录屏> <幻灯片目录> 0 <时长> 5 <偏移>      # 粗
slidematch <录屏> <幻灯片目录> <b-7> <b+9> 0.5 <偏移>  # 每个切换点细化
```

⚠️ **传给 `slidematch` 的起止时间是「录屏时间」，不是原片时间**；工具只在输出时加上偏移。我第一次就是把原片时间当录屏时间传进去，窗口全部偏了 14 秒，只测出 1 个切换点。

### job.json 里的写法

```json
"ppt": [
  { "range": [0.5, 129.5], "slide": "PPT/02.png" },
  { "range": [154.5, 263.0], "slide": "PPT/03.png" }
]
```

渲染器加一个分支：命中 ppt 区间就画幻灯片（横版铺满，竖版按 16:9 带居中），否则画裁剪后的说话头。改动量不大，等 PPT 源文件到位就能做。
